# 部署记录:Qwen2-VL-2B 在一台笔记本上是怎么变快的

这份文档按时间顺序记录每一步优化**做了什么、量到了什么、付出了什么、哪些没成**。
它回答的问题是:同一个模型、同一台机器,首字延迟和生成速度是靠哪几步降下来的,每一步各贡献多少,精度代价是多少。

- 数字的出处:README 各小节的结果表(由 `scripts/90_report.py` 从 `results/*.json` 生成)。本文只引用,不产生新数字;
  个别由表中数字相加得到的量会标明"推算"。
- 带"±"的数是逐题配对差的 95% 置信区间(同一道题上,新配置的得分减基线的得分)。区间含 0 = 与基线分不出。
- **数字只代表这台笔记本**(GPU 动态频率,CPU 跑在 WSL2 的 4 个 vCPU 上、不能绑核)。方法可以迁移,数字不能引用。
- 想看代码怎么实现的:[code-walkthrough.md](code-walkthrough.md)。

## 1. 一页结论

模型 Qwen2-VL-2B-Instruct(视觉塔 0.67B + 语言模型 1.31B),任务是"一张图 + 一个问题 → 短答案"。

### GPU 栈(TensorRT-LLM,RTX 4060 Laptop 8 GB)

| 指标 | 起点(BF16) | 优化后 | 手段 | 精度代价 |
|---|---|---|---|---|
| 首字延迟 TTFT(576 token,方图) | 290 ms | **177 ms**(1.64×) | 视觉塔换成 TensorRT FP16 引擎 | +0.18 ± 0.29(5000 题,分不出) |
| prefill(576 token) | 71 ms | **41 ms**(1.74×) | 语言模型 FP8 | −0.21 ± 0.44(5000 题,分不出) |
| decode | 70.3 tok/s | **104.4 tok/s**(1.49×) | 语言模型 FP8 | 同上 |
| decode(要吞吐时) | 70.3 tok/s | 146.6 tok/s(2.08×) | 语言模型 AWQ-INT4 | **−1.53 ± 0.70**(真掉点) |
| 权重体积 | 4.42 GB | 3.11 GB(FP8)/ 2.49 GB(AWQ) | 同上 | — |
| 加载后整卡显存 | 6133 MB | 5607 MB(FP8)/ 5180 MB(AWQ) | 同上 | — |

### CPU 栈(OpenVINO GenAI,4 线程)

| 指标 | 起点(FP16 权重) | 优化后(`int4-vis8w`) | 手段 | 精度代价 |
|---|---|---|---|---|
| 首字延迟 TTFT(256 token) | 9.77 s | **4.37 s**(2.24×) | 视觉塔 INT8 仅权重 + 语言模型 INT4 | −1.90 ± 3.11(200 题,判不了) |
| 其中视觉段 | 6.53 s | **2.90 s**(2.25×) | 视觉塔 INT8 仅权重 | |
| 其中 prefill | 3.26 s | 1.50 s(2.2×) | 语言模型 INT4 | |
| decode | 11.5 tok/s | **34.2 tok/s**(2.97×) | 语言模型 INT4 | |
| 四个子模型合计体积 | 约 4.9 GB | 约 2.1 GB | 同上 | |

### 一次完整回答要多久(推算)

用上表的 P50 相加:总时间 ≈ TTFT + (N − 1) / decode 速度。N 取各自计时时强制生成的 token 数(GPU 64、CPU 32)。
这是推算,不是实测的端到端时间,也不含引擎外的图像预处理(GPU 上另有 39–50 ms)。

| 配置 | TTFT | decode | 推算总时间 |
|---|---|---|---|
| GPU BF16,t576,64 token | 278 ms | 70.3 tok/s | 约 1.17 s |
| GPU FP8,t576,64 token | 256 ms | 104.4 tok/s | 约 0.86 s |
| GPU AWQ-INT4,t576,64 token | 290 ms | 146.6 tok/s | 约 0.72 s |
| CPU fp16,t256,32 token | 9.77 s | 11.5 tok/s | 约 12.5 s |
| CPU int4-vis8w,t256,32 token | 4.37 s | 34.2 tok/s | 约 5.3 s |

读法:**答案短(几个 token)时,时间几乎全是首字延迟,该动视觉塔;答案长时 decode 占大头,该量化语言模型。**
两个手段作用在不同的段上,可以叠加 —— "视觉塔引擎 + FP8 语言模型"这个组合本项目没有实测(见第 7 节)。

## 2. 起点

| 项 | 情况 | 带来的约束 |
|---|---|---|
| GPU | RTX 4060 Laptop,8 GB,Windows 桌面常驻占 0.5–1 GB | 模型 4.4 GB + KV cache + 引擎要精打细算;显存一满就被换到共享内存,速度掉一个数量级 |
| CPU | i9-14900HX,但 WSL2 只分到 4 个 vCPU、8 GB 内存、4 GB swap | 导出、压缩的峰值内存都贴着 8 GB;CPU 与 GPU 任务不能同时跑 |
| 系统 | WSL Ubuntu 24.04 原生安装,不用 Docker | TensorRT-LLM 的官方路径是容器,原生安装要自己解决 MPI、flash-attn 等依赖 |
| 模型 | 视觉塔 32 层(处理合并前的块,数量是图像 token 的 4 倍)+ 语言模型 28 层 | 视觉塔的计算量随分辨率增长得比语言模型快 |

跑之前写下的预测(README"要回答的问题"),后来逐条对照:

| 预测 | 实测 | 结论 |
|---|---|---|
| GPU TTFT 约 0.1 / 0.3 / 0.55 s,视觉塔占 60–75% | 120 / 278 / 484 ms,占 65 / 74 / 78% | 对 |
| decode ≈ 70 / 110 / 150 tok/s(BF16 / FP8 / AWQ) | 70.3 / 104.4 / 146.6 | 对 |
| FP8 能加速 prefill,AWQ 不能 | FP8 71 → 41 ms;AWQ 72–73 ms 不动 | 对 |
| 量化语言模型后 TTFT 几乎不变 | 278 → 255 ms(FP8),287–290 ms(AWQ) | 对 |
| 纯文本校准的 FP8 掉得更多 | 75.42 对 75.51,差 0.09 分,在噪声内 | **不成立** |
| CPU 视觉塔每张图 4–5 s,静态 INT8 约减半 | 6.53 s;静态 INT8 2.14 s(约三分之一) | 更慢;减得更多,但精度不可接受 |

先写预测再测量的用处:预测对了,说明对瓶颈的理解是对的,可以放心往下做;预测错了的那两条,正好是值得写进结论的发现。

## 3. 方法:先量后改

1. **先把一个请求拆成段,再决定优化哪一段。** 视觉编码、prefill、decode 受的限制不同(前两个受算力限制,
   decode 受显存带宽限制),一种手段通常只帮其中一段。不拆开量,就会出现"量化完了首字延迟没变"而不知道为什么。
2. **每一步只改一个东西,并且和上一步在同一批题上逐题配对。** 配对差的置信区间比两个独立分数的区间窄得多
   (5000 题时 ±0.3–0.7 分,而单个分数是 ±1.1 分),才分得出 0.5 分量级的差异。
3. **决策集与测试集分开。** 选配方、选校准数据只看 dev;test 只在最后报数。校准数据又与两者都不重叠。
4. **计时要能证明自己稳。** 交错轮次(GPU)或 ABBA(CPU)抵消频率漂移,报 P50 / P90,另报跨轮极差。

## 4. 过程记录

### 第 0 步:先让两条栈"答对"(P0,2026-11-09)

优化的前提是基线正确。三个后端(HF 参考、TensorRT-LLM、OpenVINO GenAI)答同样 8 道题,判据是与 HF **逐字**一致。

| 修掉的问题 | 现象 | 根因 |
|---|---|---|
| 缺 flash-attn 2 | TensorRT-LLM 启动即报错 | 视觉塔被写死用 flash-attn 2,而它不在 pip 依赖里 |
| 视觉塔返回值类型 | 预热时报 embedding 数量不匹配 | transformers 5.x 改了返回类型,TensorRT-LLM 仍当张量用 |
| **lm_head 全零** | 不报错,所有题都输出 `!!!!!!!!` | 权重共享标志在 5.x 的配置拆分里丢了,输出层没加载到权重 |
| 提示词多一个换行 | 8 题里 2 题答案与 HF 不同 | TensorRT-LLM 的默认输入加载器在图片占位符后多插了一个换行 |

结果:三方 8/8 逐字一致。前三个问题用一个 `sitecustomize` 修补,不改安装目录里的任何文件。
**代价**:这一步不产生任何性能数字,但没有它后面所有数字都不可信 —— 第三个问题下模型"能跑、有输出、只是全错"。

### 第 1 步:确认评测基座(P1,2026-11-10)

HF BF16、原生分辨率,复现官方分数:TextVQA 79.00 ± 1.05(官方 79.7),RealWorldQA 61.31 ± 3.45(官方 62.9)。
前者在预设的 1.5 分线内;后者差 1.59 分、超线,但数据集只有 765 题,置信半宽 ±3.45,所以另报"差是否在置信区间内",
两个判据都保留,不事后改线。逐题核对过:选项题全部答成单个字母,答错的自由作答题都是真错。

### 第 2 步:量清楚时间花在哪(P2,2026-11-10)

TensorRT-LLM BF16,三档图像 token。计时方法:每个带图请求配一个**长度逐 token 相同的纯文本请求**,
两者 prefill 计算量相同,TTFT 之差就是视觉段。

| 档位 | TextVQA | TTFT | 视觉段 | prefill | 视觉占比 | decode |
|---|---|---|---|---|---|---|
| t256 | 69.43 | 120 ms | 78 ms | 42 ms | 65% | 70.5 tok/s |
| t576 | 75.72 | 278 ms | 207 ms | 71 ms | 74% | 70.3 tok/s |
| t1024 | 79.27 | 484 ms | 377 ms | 107 ms | 78% | 70.1 tok/s |

这一步定下了后面全部工作的方向:

- **token 档位本身是最大的旋钮**:256 → 1024,精度 +9.8 分,TTFT ×4。t1024 已追平原生分辨率(79.00)。
  档位按图的信息密度选,不是越省越好。
- **视觉塔占首字延迟的 65–78%** → 只量化语言模型,TTFT 最多省 26%。这触发了第 4 步。
- 引擎外还有 39–50 ms 的图像预处理与进程间通信,纯文本请求只有 2 ms。

### 第 3 步:量化语言模型(P3,2026-11-11)

ModelOpt 把语言模型量化成 FP8(权重与激活都 8 位)或 AWQ-INT4(只压权重),各用纯文本、图文两种校准数据,共 4 个 checkpoint。
视觉塔与输出层不量化。

| 变体 | 权重 | TextVQA val 配对差 | 答案与 BF16 相同 | TTFT | prefill | decode |
|---|---|---|---|---|---|---|
| bf16 | 4.42 GB | — | — | 278 ms | 71 ms | 70.3 |
| fp8-img | 3.11 GB | −0.21 ± 0.44 | 88.2% | 256 ms | 41 ms | 104.4 |
| fp8-txt | 3.11 GB | −0.29 ± 0.45 | 85.7% | 255 ms | 41 ms | 104.4 |
| awq-img | 2.49 GB | **−1.53 ± 0.70** | 71.9% | 290 ms | 72 ms | 146.6 |
| awq-txt | 2.49 GB | **−1.73 ± 0.70** | 69.3% | 287 ms | 73 ms | 146.4 |

- **FP8 是白拿的**:精度与 BF16 分不出,prefill 快 1.74 倍,decode 快 1.49 倍。
- **AWQ-INT4 是交换**:decode 快 2.08 倍,但掉 1.5–1.7 分,prefill 不动。
- **首字延迟只降了 8%**(278 → 255 ms),视觉段 207 ms 原地不动,量化后占到 TTFT 的 84% —— 和第 2 步的预测一致。
- 图文校准与纯文本校准分不出;图文校准反而更省时间(AWQ 搜索 510 s 对 1155 s)。

**这一步最重要的教训不在速度上**:AWQ 的 −1.5 分在 1344 题的 dev 集上是 −0.78 ± 1.36,区间含 0,看起来"无损";
到 5000 题的 test 上才显著。只在千题规模上做选型,会把一个真掉点的配置放过去。

### 第 4 步:视觉塔换成 TensorRT 引擎(P5,2026-11-14 至 15)

做法沿用项目 A(纯 ViT)验证过的四条:静态形状(每个图像网格一个引擎)、位置编码常量折叠、强类型 FP16、确认注意力被融合。
引擎不是离线预计算 embedding,而是在 TensorRT-LLM 的 worker 进程里**原位替换**视觉塔 —— 这样首字延迟里仍然包含视觉段,
端到端对比才公平。

| 档位(方图) | 孤立视觉塔 | 加速 | 端到端 TTFT | 加速 | 视觉占比 |
|---|---|---|---|---|---|
| s256 | 78.1 → 37.1 ms | 2.11× | 118 → 83 ms | 1.42× | 65% → 48% |
| s576 | 209.8 → 102.1 ms | 2.06× | 290 → 177 ms | 1.64× | 75% → 59% |
| s1024 | 452.4 → 212.0 ms | 2.13× | 579 → 343 ms | 1.69× | 79% → 64% |

- 精度:TextVQA val 全量 5000 题,69.09 → 69.27,配对差 +0.18 ± 0.29,答案逐字相同 94.5%。
- 孤立测到的 2.1 倍完整带到了端到端(视觉段 217 → 104 ms,与孤立的 102 ms 只差 2 ms);prefill 与 decode 不受影响。
- 引擎的 FP16 输出比现状的 BF16 更接近 FP32 真值(最大相对误差 0.22–0.26 对 0.35–0.39),32 层注意力全部被融合。
- 显存反而降了:加载后整卡 6.1–6.2 GB → 5.3–5.4 GB(引擎接管后把 PyTorch 视觉塔挪到 CPU)。

**代价**:

- 静态形状。每个网格一个引擎,各 1.34 GB(1278 MiB),权重不共享;构建一个约 40–46 秒,导出约 20–25 秒。
- 8 GB 显存放不下三个引擎加语言模型,运行期只能加载用得到的那个网格。
- 加载时间 144–158 s → 185–206 s。
- 这里的方图是中心裁剪得到的,**裁剪本身掉 6.6 分**(s576 的基线 69.09,保持长宽比的 t576 是 75.72)。
  这一节量的是"引擎替换"的收益;落地时应按相机的固定分辨率建对应网格的引擎,而不是裁成方图。

### 第 5 步:CPU 栈压缩(P4,2026-11-15)

从同一份 FP16 IR 出发,NNCF 做 5 个配方,每个配方只替换涉及的子模型,其余硬链接。精度在 test 前 200 题上与 fp16 逐题配对。

| 配方 | 语言模型 | 视觉塔 | 配对差(n=200) | TTFT | 视觉段 | prefill | decode |
|---|---|---|---|---|---|---|---|
| fp16 | 3.09 GB | 1.33 GB | (对 GPU BF16)−0.50 ± 0.74 | 9.77 s | 6.53 s | 3.26 s | 11.5 |
| int8 | 1.55 GB | 1.33 GB | +0.55 ± 0.98 | 7.73 s | 6.50 s | 1.41 s | 23.4 |
| int4 | 0.91 GB | 1.33 GB | −1.60 ± 3.64 | 7.99 s | 6.54 s | 1.59 s | 31.9 |
| int4awq | 0.91 GB | 1.33 GB | −1.10 ± 3.22 | 7.56 s | 6.23 s | 1.53 s | 34.1 |
| **int4-vis8w** | 0.91 GB | 0.67 GB | −1.90 ± 3.11 | **4.37 s** | 2.90 s | 1.50 s | 34.2 |
| int4-vis8s | 0.91 GB | 0.67 GB | **−7.00 ± 5.35** | 3.61 s | 2.14 s | 1.52 s | 34.2 |

- **规律和 GPU 上一样**:首字延迟的大头是视觉塔(67%);只压语言模型,TTFT 只降两成。
- **视觉塔 INT8 仅权重**:不需要校准数据,压缩只要 21 秒,视觉段快 2.25 倍。这是 CPU 上性价比最高的一步。
- **视觉塔静态 INT8 不值得**:比仅权重多省 0.76 s,却掉 5–7 分;压缩要 93 分钟、峰值内存 6.97 GiB。
- 两条栈的基线一致:CPU fp16 相对 GPU BF16 是 −0.50 ± 0.74,答案相同 94%,后面的差异可以归到压缩本身。
- 同一档位 GPU 的 TTFT 是 120 ms,CPU 基线是它的约 80 倍、压缩后约 36 倍。

**这组数字的分辨率有限**:CPU 上每题约 10 秒,精度只评了 200 题,配对差的区间是 ±1–5 分,只能检出大的掉点。
INT4 的 −1.6 分区间含 0,但答案相同率只有 66%,不能说它无损。

### 第 6 步:演示与收尾(P6,2026-11-15 至 16)

`scripts/20_demo.py` 在任一变体上流式作答并打印首字延迟。它经评测用的同一个入口加载模型,所以演示的就是被评测的配置。
一次完整 `make demo` 的单次观察与基准对得上(引擎侧 TTFT,括号里是基准):t576 的 BF16 285 ms(278)、FP8 253 ms(256);
方图 s576 的 BF16 284 ms(290)、视觉塔引擎 177 ms(177);CPU 9.51 → 4.49 s(9.77 → 4.37 s)。

演示还量到了基准表里不显眼的一段:**用户实际等的时间比引擎侧多 26–72 ms**(主进程里的图像预处理加进程间通信)。
FP8 在引擎侧省下的 32 ms,到客户端只剩 322 → 315 ms —— 语言模型量化对"体感首字延迟"的帮助比表里的数字还小,
下一步该优化的是预处理(挪进 C++ / GPU)。这是 4 道题的单次观察,只说明方向,不作结论。

## 5. 让数字可信的做法

| 做法 | 防的是什么 | 在哪 |
|---|---|---|
| 图片先按官方规则预缩放到 28 的整数倍,再送进任何一条栈 | 两条栈各自插值一次,"精度差"里混进"预处理差" | `vlmdeploy/imaging.py` |
| GPU 两个后端用同一个函数生成提示词;CPU 用"输入 token 数逐题相同"核对 | 提示词差一个 token 就会改变答案 | `vlmdeploy/smoke.py`、`scripts/03_smoke_cpu.py` |
| 逐题配对差 + 95% 置信区间 | 把噪声当成掉点,或把掉点当成噪声 | `scripts/10_eval.py` |
| calib / dev / test 按图片的 SHA-1 划分,互不重叠 | 在测试集上挑配置;同一张图同时出现在校准集和评测集 | `vlmdeploy/tasks.py` |
| 带图请求 − 同长度纯文本请求,同一轮内配对相减 | 视觉段无法直接计时;两个中位数相减会带进频率漂移 | `scripts/11_bench_gpu.py` |
| 计时时关闭 KV cache 块复用 | 重复请求命中前缀缓存,prefill 变成与长度无关的 20 ms | 同上 |
| 交错轮次(GPU)/ ABBA(CPU),报 P50 / P90 与跨轮极差 | 升温降频让先测的配置占便宜 | `vlmdeploy/timing.py`、`scripts/14_bench_cpu.py` |
| 强类型 FP16 引擎 | 弱类型构建的层精度随计时漂移,两次构建结果不同 | `scripts/15_vision_trt.py` |
| 引擎与 FP32 真值对拍,同时报 BF16 现状的误差 | "引擎误差大不大"没有参照就无法判断 | 同上 |
| README 的表只由 `results/*.json` 生成 | 文档与实测脱节 | `scripts/90_report.py` |
| 评测逐题落盘、可断点续跑 | 一次两小时的评测被休眠或 OOM 打断后从头再来 | `scripts/10_eval.py` |

## 6. 踩过的坑

| 现象 | 根因 | 解决 |
|---|---|---|
| 所有题输出 `!!!!!!!!`,没有任何报错 | lm_head 没加载到权重,logits 全零,贪心解码每步选 0 号 token | 建模型前把权重共享标志补到 `text_config` |
| 纯文本 prefill 恒为 20 ms,与长度无关 | TensorRT-LLM 默认复用 KV cache 块,重复请求命中前缀 | 计时与评测都关闭块复用 |
| HF 原生分辨率评测跑到约 700 题后每题从 0.7 s 变成 4–7 s | 每种序列长度留一块缓存,显存占满后被换到共享内存 | 每 50 题归还一次 CUDA 缓存 |
| 长跑评测卡死在 MPI 上 | 父子进程通信走了会超时的网口(根因未证实) | 把 MPI 通信钉在回环口 |
| 量化 checkpoint 加载时报缺视觉塔权重 | 导出时视觉塔键名多了 `model.` 前缀 | 只改 safetensors 的头,数据区流式复制 |
| 接入引擎后 worker 报 `Impossible to fit in any sequence in kvCache` | 三个引擎各 1.34 GB 全部常驻 | 只加载用得到的网格 |
| 接入引擎后 s1024 档起不来(KV 只剩 384 token) | 引擎与 PyTorch 视觉塔是同一份权重的两份拷贝,都在显存里 | 权重加载完就把 PyTorch 那份挪到 CPU |
| 视觉塔 ONNX 导出断言失败 | transformers 5.x 给 SDPA 传了导出器不支持的参数 | 导出期间关掉那条分支(数值不变) |
| 引擎计时偏大且不稳 | 引擎跑在另一条 CUDA stream 上,量到的是主机等待 | 引擎跑在 PyTorch 的当前 stream 上 |
| 视觉塔静态量化两次让整个 WSL 虚拟机 OOM | NNCF 一次挂上 584 个统计点,编译出的统计模型放不下;与校准样本数无关 | 按目标节点分批收集统计,每批 40 个;整个压缩进程的峰值 6.97 GiB |
| 连续提交的评测"只跑了第一条" | 评测进程读走了标准输入,后面的命令被吃掉 | `make eval` 的标准输入接 `/dev/null` |
| `make report` 会把没有结果文件的小节刷空 | P0–P3 的结果文件在仓库丢失后没有恢复 | `make report ONLY="P4 P5 DEMO CPP"` |
| C++ 程序编译不了:找不到 GenAI 的头文件 | pip 的 `openvino-genai` 轮子只有库,没有 C++ 头文件 | 按已装库的提交号从官方仓库取同一个提交的头文件(`envs/fetch_genai_headers.sh`) |
| C++ 程序加载的线程库与 Python 不同 | GenAI 的库依赖 TBB 却没写搜索路径,默认的 RUNPATH 不管"依赖的依赖",落到了系统的 `libtbb` | 链接时改用 RPATH(`-Wl,--disable-new-dtags`),`ldd` 确认指向 `openvino` 轮子里那一份 |
| C++ 试跑的首字延迟只有 2.5 s(应约 4 s) | 预热和第 1 个正式请求是同一张图同一个问题,管线复用了 KV cache,prefill 从约 1.5 s 变成 0.09 s | 预热改用另一张图(清单里的最后一个请求),Python 侧的对照同样处理 |

有三处值得单独说:

- **"误差形态本身就是线索"。** 输出固定是 0 号 token,说明是 logits 全零而不是乱码,顺着这个形态才查到输出层。
  prefill 恒为 20 ms 也一样:一个不随输入变化的"常数",本身就是缓存命中的痕迹。
- **减校准样本救不了 OOM。** 第一反应是减样本,但只喂 1 条样本内存照样 15 秒涨到 7.4 GiB。量了三种分批大小下
  单批统计收集的峰值(40 / 80 / 160 个节点:5.30 / 6.31 / 7.16 GiB)之后才定下每批 40 个;正式压缩时整个进程的峰值是
  6.97 GiB(统计收集之后还有偏置校正等步骤)。
- **显存账要算到"同一份权重有几份拷贝"。** 引擎接进来之后 KV cache 从 478 个块掉到 12–39 个,多占的 1.6 GB
  与"引擎 1.34 GB + PyTorch 视觉塔 1.3 GB 同时驻留"同量级。

## 7. 没做的与局限

- **加速比没有置信区间**:表里的倍数是两个 P50 相除;`timing.ratio_ci` 能给 bootstrap 区间,但没有接进计时脚本。
- **没有实测的组合**:GPU"视觉塔引擎 + FP8 语言模型"(按分段数字应当还能再降,但没有量过);
  CPU"语言模型 INT8 + 视觉塔 INT8 仅权重"(精度优先时的推荐,同样没有量过)。
- **CPU 精度只有 200 题**,配对差区间 ±1–5 分;INT4 是否掉点在这个规模上判不了。
- **视觉塔静态 INT8 掉 5–7 分的原因没有查**:没有做逐层敏感度分析,也没有用 accuracy control。
- **加速来自哪些 kernel 没有逐层剖析**:FP8 / AWQ 对 prefill、decode 的不同影响,只说与"算力受限 / 带宽受限"的解释一致。
- **方图档位是中心裁剪**,掉 6.6 分;非方图网格的引擎没有建。
- **P0–P3 的原始结果文件不在仓库里**:2026-11-12 本机仓库目录丢失,源码与提交历史由开发记录重建,
  README 中 P0–P3 的表是丢失前生成的内容;P4、P5、演示是重建后完整重跑的。
- 仓库重建后,`02_smoke_gpu.py`、`03_smoke_cpu.py`、`12_quantize_gpu.py` 只做过静态检查与导入检查,没有重新执行
  (`00_download_model.py` 重新执行过:本地权重与 Hub 公布的 sha256 一致)。
- 演示第一次跑视觉塔引擎档时,引擎侧 TTFT 是 427–558 ms,之后三次运行都是 158–178 ms,没有复现,原因未查明;
  那一次的记录已被覆盖,只留在当时的终端输出里。
- **只有 CPU 栈有 C++ 程序**(`cpp/vlm_infer_ov`,2026-11-21 补):与 Python 逐题对拍,16 道 dev 题回答逐字相同,
  首字延迟之比 1.008(在两遍测量的漂移之内)。只在 `ov-int4-vis8w` 这一个变体、t256 档上核对过;
  C++ 程序自己不做预缩放,对拍用的图是 Python 预缩放后存成 PNG 的。GPU 栈没有:TensorRT-LLM 用的是 PyTorch 后端,
  语言模型是 PyTorch 模块、生成循环在 Python 里,没有引擎文件可交给 C++(纯 TensorRT 手写循环、引擎后端两条路线都没有做)。
- 仓库没有远端、没有持续集成;代码许可未定。

## 8. 复现

```bash
make env-trtllm env-ovgenai   # 两个 conda 环境
make model data               # 模型 4.43 GB + 数据 1.9 GB,逐文件校验 sha256
make test                     # 单元测试
make p1 p2 p3                 # 评测基座、GPU 基线、GPU 量化(约 7 小时)
make p5                       # 视觉塔引擎
make p4                       # CPU 栈(必须在 GPU 任务全部结束后跑)
make demo                     # 演示
make cpp-cpu parity-cpu       # CPU 栈的 C++ 程序:构建,与 Python 逐题对拍 + 配对计时
make report                   # 回填 README 的表
```

每一步都可断点续跑。单项评测:`make eval VARIANT=trtllm-fp8-img SPLIT=dev BUDGET=t576 PAIRED=trtllm-bf16`。
